# Core / Identity / Tenancy — Data Dictionary

Canonical DDL authority for the core-identity tables authored by their owning
phase (Plan §13.2). Phase R3 (REM-MFA-001) authored the two MFA tables below;
the remaining as-built core-identity tables (`users`, `magic_login_tokens`,
`merchants`, `merchant_users`, …) are summarised in Plan §13.5 and will get
their full entries in their owning reconciliation phase.

---

## `mfa_credentials` (Phase R3 — REM-MFA-001)

- **Domain owner:** `app/Domain/Auth` (identity/authentication).
- **Purpose + scope refs:** stores a user's confirmed TOTP authenticator
  (RFC 6238) for privileged MFA and step-up. Plan §13.5, §17, §18, §9.4 step 2.
- **Tenant ownership:** **none** — identity-owned, not merchant-scoped. MFA is a
  property of the `users` row, resolved before tenant context (Plan §18
  enforcement order). No `merchant_id`/`branch_id`; not covered by
  `BelongsToMerchant`.
- **Primary key:** `id bigint generated by default as identity`.
- **Public identifier:** `ulid char(26)` unique (Plan §13.1; used if a
  credential is ever externally referenced, e.g. an admin recovery view).

| Column | Type | Null | Default | Meaning |
|---|---|---|---|---|
| `id` | bigint identity | no | — | internal PK |
| `ulid` | char(26) | no | generated | public identifier (unique) |
| `user_id` | bigint | no | — | FK → `users.id` `ON DELETE RESTRICT` (financial/audit-grade identity link) |
| `type` | varchar(20) | no | `'totp'` | credential type; `CHECK (type IN ('totp'))` |
| `secret_encrypted` | text | no | — | TOTP shared secret, **encrypted at rest** via Laravel `encrypted` cast (AES-256-GCM, `APP_KEY`). Never logged/audited/returned after enrollment. |
| `confirmed_at` | timestamptz | yes | null | set when the first valid TOTP confirms enrollment. `null` ⇒ unconfirmed (abandoned enrollments are safely overwritten). |
| `last_used_at` | timestamptz | yes | null | timestamp of the most recent successful verification (forensics; never the code). |
| `last_used_timestep` | bigint | yes | null | RFC 6238 replay-prevention state: the time-step index of the last accepted code. A new code must verify with a **strictly newer** step (`verifyKeyNewer`), so a code cannot be replayed within or before its window. |
| `created_at` / `updated_at` | timestamptz | no | — | row timestamps |

- **Foreign keys:** `user_id → users(id) ON DELETE RESTRICT ON UPDATE CASCADE`.
- **Unique constraints:** `UNIQUE (user_id, type)` — **one active credential per
  user** (one TOTP authenticator per user).
- **Indexes:** unique `(ulid)`, unique `(user_id, type)`.
- **Encryption/hashing/redaction:** `secret_encrypted` encrypted at rest; the
  plaintext secret and otpauth URI are returned **only** through the
  authenticated enrollment-start response and never persisted in plaintext,
  logged, cached, or written to audit context (Plan §9 rule 13).
- **Soft-delete policy:** none; a credential is hard-deleted only when MFA is
  reset by a future, separately-authorized account-recovery workflow (deferred).
- **Immutability:** rows are mutable only for `confirmed_at`, `last_used_at`,
  `last_used_timestep`, `updated_at` and (on re-enrollment) `secret_encrypted`.
- **Audit events:** `mfa.enrollment_started`, `mfa.enrollment_confirmed`,
  `mfa.challenge_succeeded`, `mfa.challenge_failed` (Plan §70 / R2 chain).
- **Migration order:** after `users`; forward-only; no backfill (new table).
- **Concurrency:** confirmation/verification run inside a DB transaction; the
  replay step uses `last_used_timestep` compare-and-set.
- **Tests:** `MfaEnrollmentTest`, `MfaChallengeTest`, `MfaSecretRedactionTest`.

## `mfa_recovery_codes` (Phase R3 — REM-MFA-001)

- **Domain owner:** `app/Domain/Auth` (identity/authentication).
- **Purpose + scope refs:** one-time recovery codes that substitute for a TOTP
  code in the challenge contract when the authenticator is unavailable. Plan
  §13.5, §18.
- **Tenant ownership:** **none** — identity-owned (see `mfa_credentials`).
- **Primary key:** `id bigint generated by default as identity`.
- **Public identifier:** `ulid char(26)` unique (Plan §13.1).

| Column | Type | Null | Default | Meaning |
|---|---|---|---|---|
| `id` | bigint identity | no | — | internal PK |
| `ulid` | char(26) | no | generated | public identifier (unique) |
| `user_id` | bigint | no | — | FK → `users.id` `ON DELETE RESTRICT` |
| `code_hash` | char(64) | no | — | SHA-256 hex of the high-entropy raw recovery code. The raw code is shown **once** at generation and never stored/logged. |
| `used_at` | timestamptz | yes | null | set atomically on single-use consumption; `null` ⇒ still usable |
| `created_at` / `updated_at` | timestamptz | no | — | row timestamps |

- **Foreign keys:** `user_id → users(id) ON DELETE RESTRICT ON UPDATE CASCADE`.
- **Unique constraints:** `UNIQUE (code_hash)`.
- **Indexes:** unique `(ulid)`, unique `(code_hash)`, composite
  `(user_id, used_at)` for "this user's unused codes" lookups.
- **Encryption/hashing/redaction:** stored only as SHA-256 hashes; raw codes are
  CSPRNG-generated, displayed once, never persisted in plaintext or logged.
- **Single-use:** consumed by an atomic conditional update
  `UPDATE … SET used_at = now() WHERE user_id = ? AND code_hash = ? AND used_at IS NULL`
  that must affect exactly one row, so concurrent attempts cannot both succeed.
- **Lifecycle:** generated **only after** successful TOTP confirmation;
  regenerating replaces the full set (old unused codes are deleted) and is
  protected by fresh step-up.
- **Audit events:** `mfa.recovery_code_used`, `mfa.recovery_codes_regenerated`.
- **Migration order:** after `users`; forward-only; no backfill.
- **Tests:** `MfaRecoveryCodeTest`, `MfaSecretRedactionTest`.

## `idempotency_keys` (Phase R4 — REM-IDEMP-001)

- **Domain owner:** `app/Domain/Idempotency` (cross-cutting request/replay
  protection).
- **Purpose + scope refs:** durable store guaranteeing that a duplicate,
  concurrent, or recoverable-retry request produces exactly one effect, and that
  a completed request replays its original (encrypted, sanitised) response. Plan
  §13.5 (corrected schema, Correction 3.2), §24.4 (algorithm), §8 ADR-003.
- **Tenant ownership:** **optional** — a row is *scoped* by the derived
  `idempotency_scope` string (which embeds the merchant/user/provider identity),
  with `merchant_id`/`branch_id`/`actor_user_id` carried as **nullable** columns
  for forensics and FK integrity. It is not a `BelongsToMerchant` model: platform
  and provider-webhook scopes have no merchant. Isolation is enforced by the
  scope being part of the unique key, so the same raw key under different
  merchants/actors/provider environments can never collide.
- **Primary key:** `id bigint generated by default as identity`.
- **Public identifier:** `ulid char(26)` unique (Plan §13.1; never exposed in
  replayed responses).

| Column | Type | Null | Default | Meaning |
|---|---|---|---|---|
| `id` | bigint identity | no | — | internal PK |
| `ulid` | char(26) | no | generated | public identifier (unique) |
| `idempotency_scope` | varchar(191) | no | — | deterministic scope, e.g. `merchant:{ulid}:user:{ulid}`, `platform:user:{ulid}`, `webhook:{provider}:{env}` |
| `key_hash` | char(64) | no | — | **SHA-256 of the raw `Idempotency-Key`** (the raw key is never stored) |
| `actor_user_id` | bigint | yes | null | FK → `users.id` `ON DELETE SET NULL` (forensics) |
| `merchant_id` | bigint | yes | null | FK → `merchants.id` `ON DELETE RESTRICT` (forensics) |
| `branch_id` | bigint | yes | null | FK → `merchant_branches.id` `ON DELETE RESTRICT` (forensics) |
| `route_name` | varchar(191) | no | — | the named route the key claimed |
| `http_method` | varchar(10) | no | — | request method |
| `request_content_type` | varchar(100) | yes | null | request content type (part of the canonical hash) |
| `request_hash` | char(64) | no | — | SHA-256 canonical request hash (method+route+normalized path params+content type+recursively-canonicalised body) |
| `state` | varchar(20) | no | — | `CHECK in ('processing','completed','failed')` |
| `response_status` | smallint | yes | null | stored HTTP status for replay |
| `response_headers` | jsonb | yes | null | **allowlisted, safe** response headers only |
| `response_body_encrypted` | text | yes | null | replay-safe JSON body, **encrypted at rest** (`encrypted` cast) |
| `locked_at` | timestamptz | no | — | when the current execution lock was taken |
| `lock_expires_at` | timestamptz | no | — | lock expiry; a lock is "active" while `> now()` |
| `completed_at` | timestamptz | yes | null | when the row reached `completed` |
| `failed_at` | timestamptz | yes | null | when the row reached `failed` |
| `last_error_code` | varchar(100) | yes | null | redacted error code for a `failed` row (never a message/stack) |
| `expires_at` | timestamptz | no | — | retention horizon for pruning |
| `created_at` / `updated_at` | timestamptz | no | — | row timestamps |

- **Foreign keys:** `actor_user_id → users(id) ON DELETE SET NULL`;
  `merchant_id → merchants(id) ON DELETE RESTRICT`;
  `branch_id → merchant_branches(id) ON DELETE RESTRICT`.
- **Unique constraints:** `UNIQUE (idempotency_scope, key_hash)` — the correctness
  boundary: a second concurrent claim of the same scope+key fails the insert and
  is routed to replay / in-progress / conflict.
- **Indexes:** unique `(ulid)`, unique `(idempotency_scope, key_hash)`,
  `(state, lock_expires_at)` (expired-lock recovery scans), `(expires_at)` (prune).
- **Encryption/hashing/redaction:** only `SHA-256(raw key)` is stored; the
  response body is encrypted at rest; `response_headers` is a tiny allowlist
  (never `Set-Cookie`, `Authorization`, `X-XSRF-TOKEN`, session/CSP/signed-URL/
  debug headers); `last_error_code` is a redacted code, never a stack/SQL/secret.
- **Soft-delete policy:** none; rows are hard-deleted by `idempotency:prune` only
  past `expires_at`, and **never** while a `processing` lock is active.
- **Concurrency:** claims run inside a DB transaction; the unique constraint
  serialises first-claim races, and expired-lock recovery uses
  `SELECT … FOR UPDATE` so only one worker reclaims an abandoned lock.
- **Retention:** standard completed rows ≥ 72h; support-retriable financial rows
  configurable ≥ 30 days; provider-dedupe rows live with their future financial
  record (Phase 20D).
- **Migration order:** after `users`, `merchants`, `merchant_branches`;
  forward-only; no backfill. Replaces the prior **invalid** definition (no
  `key_hash`) which never existed in the repo (Plan §4 finding 9).
- **Audit events:** none of its own (it is infrastructure); the protected domain
  action emits its own audit event.
- **Tests:** `IdempotencySchemaTest`, `CanonicalRequestHashTest`,
  `IdempotentReplayTest`, `IdempotencyConflictTest`, `IdempotencyConcurrencyTest`,
  `ExpiredLockRecoveryTest`, `ReplayResponseSecurityTest`, `IdempotencyPruneTest`,
  `ProviderCallbackDedupeSeamTest`, `FinancialRouteIdempotencyCoverageTest`.
