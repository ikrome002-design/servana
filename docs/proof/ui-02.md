## Phase

`UI-02` — Multi-host foundation. Third phase of the corrective UI programme
(`Servana_Role_Specific_UI_UX_Subdomain_Software_Development_Plan.md` §25).

## Objective

Implement the eight-host architecture safely so each canonical host resolves to the correct
public account context, the production Docker/Nginx deployment serves a working Servana SPA
with resolvable chunks and approved brand assets, unknown hosts fail safely, host context
never grants authorization, and later phases can bind authentication, content, navigation and
account experiences to a reliable host foundation.

**Boundary.** UI-02 does not complete the eight public landing pages (UI-06), does not bind
Magic Links or sessions to hosts (UI-03), and does not redesign any page (UI-04, UI-08…UI-15).

## Root-cause records

Full Bug Fix Protocol records — observed problem, evidence, affected files, root cause, why it
is the root cause, correct fix, files changed, tests, test command, test result,
production-image proof, proof of resolution, remaining risk — are in
`docs/frontend/audits/ui-02/defect-closure.json`. Summary of the four root causes:

1. **`UI01-PROV-001`** — the root route was bound to the untouched scaffold view. Nothing in
   Nginx or Vite could have changed the response body, so replacing the route is the smallest
   correct fix.
2. **`UI01-PROV-002`** — a *path-ownership collision*, not a base-path mistake. Two owners
   wanted `/assets/`: Vite's default output directory and Laravel's public tree. Changing
   `base` alone would have moved the collision rather than removed it. One prefix per owner
   (`/spa-assets/` vs `/assets/`) removes it by construction.
3. **`UI01-HOST-001`** — the eight-host architecture was *adopted* in UI-00 but had no runtime.
   Every downstream symptom followed from the absence of a host concept.
4. **`UI01-ASSET-005`** — two roots. The files were present and correctly cased throughout;
   only the origin serving the shell lacked them.

### A fifth root cause, found and fixed inside this phase

Rehearsing the smoke against the **built images** (rather than the bind-mounted dev stack)
returned `500` on every browser route: `The SPA manifest is missing at
public/spa/.vite/manifest.json`.

`public/spa` is in `.dockerignore`, the SPA is built into the **nginx** image, and
`docker-compose.prod.yml` shares no volume between `app` and `nginx` — so the manifest the
shell reads was simply absent from the application image. The dev stack hid this because both
containers bind-mount the same `./public`.

Fixed by adding a `spa-manifest` build stage to `docker/php.Dockerfile` and copying **only**
the manifest into the prod image; the chunks stay owned by the edge. This is exactly why §12.5
requires the real production topology rather than `vite preview` — the defect was invisible in
every other harness.

## Authorization-denial proof

`AccountHostDoesNotAuthorizeTest`:

- an anonymous request on `citrus.servana.test` is `401` — arriving on the platform host
  authenticates nobody;
- one unauthenticated protected call swept across **all 24 approved hosts** returns `401` on
  every one, so no host is an authorization input;
- a platform-data request is refused **identically** on the platform host and the merchant
  host;
- a structural guard proves no file outside `app/Http/Hosts/` (plus the shell, host middleware
  and health controller) references `AccountHost` — a policy that accepted one would make the
  `Host` header an authorization input by construction;
- no policy takes a `$host`/`$domain`/`$subdomain` argument.

**A note on how the sweep is written.** Laravel's test client builds the request from the URI
and Symfony's `Request::create()` overwrites `HTTP_HOST` with the URI host — so
`withHeader('Host', …)` on a relative path is silently ineffective and every call would hit
`localhost`. The first draft of these tests did exactly that and passed vacuously. They now use
absolute URLs, which is the only way the assertions genuinely vary the host.

### UI-01 evidence: rewritten by the required suite, then restored

§19.4 requires the full repository Playwright suite to run once, and that suite contains UI-01's
evidence-capture spec. Running it therefore re-captured screenshots (139 new files tagged


`docs/frontend/audits/ui-01/` is clean. The only intentional UI-01 change in this branch is the
merge-closure section appended to `docs/proof/ui-01.md`.

**Observation for UI-16 (recorded, not fixed):** an evidence-capturing spec inside the default
suite means any full local run dirties committed audit artifacts. ADR-025 requires snapshot
updates to be a reviewed act, so the capture ought to be opt-in (a tag or env flag) rather than
default. That is browser-evidence policy and belongs to **UI-16**; UI-02 does not change the
UI-01 spec.
