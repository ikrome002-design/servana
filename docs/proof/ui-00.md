# Phase UI-00 — Plan Adoption and Source Reconciliation

## Phase

`UI-00` — Plan adoption and source reconciliation. The first phase of the corrective UI programme
defined by `Servana_Role_Specific_UI_UX_Subdomain_Software_Development_Plan.md` §25.

## Objective

Adopt the role-specific UI/UX plan as the governing delivery plan for Servana frontend work, and
prove every source document, account mapping, content directory, legal directory, brand asset,
supplied landing image and binding page specification that later UI phases will implement against —
so that no implementation guess about a source path, role mapping, count or authority remains.

**This phase changes no runtime behaviour.** No route, API, policy, migration, permission,
component, style, asset or legal byte was modified.

## Root-cause records

- **G1/G2 — root cause:** the corrective UI programme is new; no adoption commit had ever been made.
  Not a regression.
- **G3/G4/G5 — root cause:** `CLAUDE.md` and `AGENTS.md` were written from an *expected* repository
  layout and never reconciled against the actual one. `docs/PROGRESS.md:2412` had noted "repository
  wins" for the landing path, but the correction was recorded in a progress log instead of in the
  workflow document that agents actually read — so the wrong path kept being used. The fix is to
  correct the workflow documents themselves and make the claim machine-checked.
- **G6 — root cause:** the screen inventory was built (Phase 11) before any full page contract
  existed, so "what exists" was the only register there was. Adding a second register is the fix;
  merging them would destroy the distinction.
- **G7 — root cause:** the Phase 23 traceability guard modelled only the backend roadmap because that
  was the only roadmap when it was written.
- **G8 — root cause:** lifecycle promotion is performed by the *next* phase's branch, by convention.
  UI-00 is that next branch.
