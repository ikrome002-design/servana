## Phase

`UI-03` — Fourth phase of the corrective UI programme
(`Servana_Role_Specific_UI_UX_Subdomain_Software_Development_Plan.md` §25).

## Objective

Bind authentication to the correct account host, and support secure multi-role account-context
switching in which the target host receives only freshly re-evaluated target authority.

**Boundary.** UI-03 implements the functional security flow only. It does not redesign the profile
or switch control (UI-04), does not build the content pipeline (UI-05), the landing pages (UI-06),
the 160-page route contract (UI-07) or any account experience (UI-08 … UI-15).

## Root-cause records

### RC-1 — `UI01-ROLE-001`: cross-role platform surface exposure

- **Observed problem.** All seven merchant-side account fixtures could request `/platform` and the
  router rendered the Super Administrator landing.
- **Governing requirement.** UI/UX plan §5.4; ADR-017; phase brief §16.3.
- **Evidence.** `docs/frontend/audits/ui-01/defect-register.csv` row `UI01-ROLE-001`;
  `platform.ts` `beforeEnter: [requiresAuth]`.
- **Affected files/routes.** `resources/spa/src/router/routes/platform.ts`,
  `resources/spa/src/router/guards.ts`.
- **Attacker and impact.** T2 (a low-privilege insider with a real session). The backend refused the
  data, so no record leaked — but the surface itself was disclosed, and a wrong-account deep link
  rendered a broader account's chrome while its API calls failed behind it.
- **Root cause.** The route tree declared no owning account, so nothing could check one. The
  existing `requiresRole` guard was never attached, and would have been the wrong instrument anyway:
  it compares a client-held role string rather than asking the server what the user may enter.
- **Why this is the root cause.** Removing the navigation entry would have hidden the door, not
  locked it; the route was reachable by typing the URL.
- **Correct fix.** A new `requiresAccount(accountKey)` guard requiring THREE things to agree before
  an account surface mounts: the route's own account, the account the **server** resolved for the
  host, and an account the **server** says the user currently holds (`/me.account_keys`, derived
  from live membership rows by `AccountContextResolver`). A mismatch renders the role-safe
  `access-denied` state — never a redirect to another account.
- **Files changed.** `guards.ts`, `routes/platform.ts`, `router/index.ts`,
  `pages/auth/AccessDenied.vue`, `stores/authStore.ts`, `types/models.ts`,
  `app/Http/Resources/Auth/AuthenticatedUserResource.php`.
- **Tests.** `resources/spa/src/router/accountRouteGuard.spec.ts` — 13 tests, one per merchant
  account plus the platform-user, no-host-context, no-account-keys, anonymous and
  no-client-computation cases.
- **Test result.** 13 passed.
- **Remaining risk.** The guard is UX. The backend remains the boundary and is independently proven
  by `AccountHostDoesNotAuthorizeTest` (unchanged, still green). UI-07 owns attaching the same guard
  to the remaining seven account trees as it builds their route contracts; UI-03 attached it where
  the proven exposure was.

### RC-2 — `UI03-AUTH-001`: HTML browser request to a protected API route returned 500

- **Observed problem.** An HTML-accept request to an auth-protected `/api/v1` route returned `500`
  (recorded in `docs/proof/ui-02.md`, assigned to UI-03).
- **Governing requirement.** UI/UX plan §5.4; phase brief §16.4.
- **Evidence.** The Increment-1 repro above asserted `500` and passed.
- **Affected files/routes.** `app/Providers/AppServiceProvider.php`; every `auth`-guarded route.
- **Attacker and impact.** T3 and ordinary users. A 500 is an availability and information-quality
  defect: it tells an operator nothing, and it tells a prober that something unusual happened.
- **Root cause.** Laravel's exception handler falls back to `route('login')` when an
  `AuthenticationException` carries no redirect target. Servana is an SPA and has never had a named
  `login` route, so the fallback raised `RouteNotFoundException`. JSON callers were unaffected
  because `Authenticate::unauthenticated()` passes `null` for them.
- **Why this is the root cause.** The route genuinely does not exist
  (`Route::has('login') === false`, asserted permanently), so nothing downstream could have
  produced a correct answer.
- **Correct fix.** `Authenticate::redirectUsing()` — the framework's own hook — supplies a
  destination, so `route('login')` is never reached. The destination is a **relative** path by
  construction, which is what makes it impossible for an attacker-controlled `Host` or
  `X-Forwarded-Host` to steer it, impossible to move a user toward a broader account host, and
  impossible to loop (`/auth/login` is public on every account host). Backend-owned and
  authentication paths are dropped from the preserved intended path rather than echoed back.
- **Tests.** `tests/Feature/Sessions/UnauthenticatedBrowserRedirectTest.php` — 9 tests.
- **Test result.** 9 passed.
- **Proof of resolution.** The `/api/v1` surface now answers `401` with the standard envelope for
  any Accept header (correct: an endpoint is not a page), and a genuine browser **page** navigation
  redirects to the same host's `/auth/login?redirect=…`.
- **Remaining risk.** No authenticated page route exists yet, so the redirect path is proven against
  a route registered inside the test. UI-07 owns the real authenticated page contract; the guard is
  in place before those pages arrive rather than after.

### RC-3 — Magic Links were bound to identity and lifetime, never to a host

- **Observed problem.** A link issued on one account host consumed successfully on any other.
- **Governing requirement.** ADR-019; UI/UX plan §5.1.
- **Root cause.** `magic_login_tokens` carried no account, host, environment, audience or redirect,
  so there was nothing for consume to compare.
- **Correct fix.** Expand-only migration adding the six binding columns, with a shaped CHECK making
  the invariant permanent (`any row that is still usable must be fully bound`), and every in-flight
  unconsumed link invalidated on upgrade so no unbound credential survives. The bindings are
  verified **inside** the single atomic consume update, which is what stops a wrong-host attempt
  from burning a legitimate user's token while still being unable to use it.
- **Tests.** `MagicLinkHostBindingTest` (22), `SessionSchemaContractTest` (17).
- **Remaining risk.** None known. A first-click attacker with mailbox access still wins; that is
  inherent to passwordless email auth and is named as a future enhancement, not solved here.

Two observations are worth stating separately because they were **not** what the matrices assumed:

- **A wrong-host handoff presentation burns the token** (OBS-19b). Any rejection invalidates the
  handoff, so a token presented on the wrong host cannot then be retried on the right one. The proof
  therefore mints a separate handoff for every negative case; presenting on the wrong host first
  would have destroyed the token under test.
- **A cross-host deep link never reaches the route guard** (OBS-33b). Host-only cookies mean the
  browser sends nothing to the other account host, so the user arrives anonymous and gets that
  host's login page. The guard's access-denied path is reached on the user's **own** host (OBS-33),
  and that is the case recorded against `AF-018` / `CS-023`.

## Security proofs

- **Host binding.** Success on the bound host for all eight accounts; denial on all 23 other
  approved hosts; account substitution, environment substitution and redirect substitution all
  denied. Every denial body is **byte-identical** (asserted), while the audit trail still
  distinguishes a substitution attempt from an expiry.
- **Replay and concurrency.** Magic Link replay denied; two consecutive service-level consumes
  yield exactly one success; two consumes of one handoff yield exactly one target session, under a
  row lock plus a conditional single-use update.
- **Authorization denial.** A Personnel-only user requesting a Finance link gets the same uniform
  202 and no email as a non-existent address.
- **Tenant isolation.** The context list for a multi-merchant user names each merchant explicitly
  and contains no foreign merchant's name; internal ids never leave the server.
- **Branch isolation.** A branch-scoped role with no active assignment produces no context at all;
  withdrawing one assignment revokes only that branch's sessions, and a second branch survives.
- **Own scope.** Session inspection and revocation are `user_id`-scoped end to end; a foreign
  session ULID returns 404, never 403.
- **MFA.** A Magic Link asserts no MFA. The target session records the requirement freshly resolved
  at creation and starts with `mfa_verified_at` **forgotten**, so an unprivileged source session
  cannot mint a satisfied privileged target.
- **Cookies / Sanctum / CORS / proxy.** `SESSION_DOMAIN` empty (host-only) and documented as such;
  stateful domains derived from the registry with no wildcard; no `cors` config and no `HandleCors`
  middleware exists, so the application is same-origin only; emitted URLs come from
  `AccountHostUrlGenerator`, proven against a poisoned `X-Forwarded-Host`.
- **Secrets.** Raw Magic Link and handoff tokens appear in no stored attribute, no audit row and no
  log; the IP and user agent on a handoff are hashed; `session_id` and `token_hash` are hidden from
  serialization.
