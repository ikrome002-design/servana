## Root-cause records

### 1 — The compiled sources interleave copy with build instructions

**Observed problem.** Rendering a compiled landing section verbatim would publish `**CTA:** **GET
STARTED**`, `**Navigation Links:** Features | How It Works | …`, `**Best Hero Image Direction:** …`
and `**Meta Title:** …` to a visitor as body copy.

**Evidence.** 62 distinct `**Label:**` annotations across the eight documents, plus 13 standalone
all-caps CTA markers.

**Affected files.** All eight `docs/landing_page/*.md`, consumed through
`content/generated/<account>/landing.generated.ts`.

**Root cause.** The approved documents are written for a human page-builder, not for direct
rendering. They mix reader-facing copy with production annotations addressed to whoever builds the
page.

**Why this is the root cause.** UI-05 correctly preserved the bodies verbatim — that is what makes
the content trustworthy — so the mixing is a property of the source, not a compilation defect.

**Correct fix.** `content/landing/landingSection.ts` CLASSIFIES lines without changing a single
word. The annotation vocabulary is **closed**: every label is classified as an instruction (dropped
with its body, and reported), editorial copy (label dropped, content kept), or content (label and
content both rendered). `landingSection.spec.ts` scans all eight real documents and fails on an
unclassified label, so a future source edit breaks the build rather than publishing an instruction —
or silently swallowing a paragraph.

**Files changed.** `resources/spa/src/content/landing/landingSection.ts` (new).

**Tests.** `landingSection.spec.ts` — 14 cases including the vocabulary-completeness scan, the
duplicate-class guard, and a per-account assertion that no standalone CTA marker and no surviving
annotation reaches the rendered output.

**Test result.** 14/14 pass. Two source phrases that MENTION `GET STARTED` inside real copy —
Branch's FAQ question "What happens when I click GET STARTED?" and Human Resource's step "Use GET
STARTED to create a business account or log in" — are preserved, because removing them would be
editing approved copy. The assertion is structural (a block whose ENTIRE text is a marker), not a
keyword ban.

**Remaining risk.** Recorded as `UI06-CTA-002`: those two phrases now name an action their pages do
not offer. Rewriting them is the product owner's call.

### 2 — Two theme controls on one page

**Observed problem.** Eight browser tests failed with `strict mode violation:
getByTestId('theme-toggle') resolved to 2 elements`.

**Evidence.** `LandingHeader.vue` rendered `SvThemeToggle`, and `SvFixedFooter.vue` — present on
every public page through the layout — rendered another.

**Root cause.** The header was given a theme control it did not need. Plan §11.1 places the theme
control in the fixed footer, which every public page already has.

**Why this is the root cause.** The failure is not a locator problem. Two switches for one setting
is ambiguous to a screen-reader user regardless of what any test asks for; the strict-mode violation
is the symptom that made it visible.

**Correct fix.** The header's copy was removed rather than the test being disambiguated with
`.first()`.

**Files changed.** `resources/spa/src/components/landing/LandingHeader.vue`.

**Test result.** 95/95 browser tests pass; the eight theme tests confirm one control, light default,
explicit dark, and persistence across reload.

**Classification.** New-code defect.

### 3 — The audit generator read the route table with a regular expression

**Observed problem.** The first `public-route-matrix.json` reported `auth.login` at `/auth`, every
HR child under `/auth/…`, and no `public.legal` at all.

**Evidence.** 116 routes exist; the regex found 34, three families wrong.

**Root cause.** The generator parsed route records out of source TEXT. `public.legal`'s path is
built from a template literal, and nested children carry a relative path the text does not resolve.

**Why this is the root cause.** The regex succeeded. It matched something, produced a plausible
artifact, and every assertion built on that artifact would have been vacuous — the exact failure
mode the file's own comment warns about.

**Correct fix.** The generator loads the route MODULES through Vite's SSR transform and walks the
records, applying vue-router's own parent/child path rule. The router itself is not imported because
`createWebHistory()` needs a browser.

**Files changed.** `scripts/generate-ui06-artifacts.mjs`.

**Test result.** 116 routes with correct absolute paths and all five aliases.
`Ui06GeneratedArtifactStalenessTest` asserts the generator uses `ssrLoadModule` and no longer
carries the text-parsing loop.

**Classification.** New-code defect, found before it reached a gate.

### 4 — Four contract tests failed on Pest's variadic `toContain`

**Observed problem.** Four of 46 PHP contract tests failed asserting things that were true.

**Root cause.** `expect($x)->toContain($needle, $message)` is **variadic** in Pest: the second
argument is another needle, not a failure message. A fifth failure came from scanning a whole
component file for `<blockquote` and matching the component's own documentation of why it renders
none.

**Correct fix.** Message arguments removed from `toContain`; the required-route set asserted in one
variadic call; the quotation-styling scan narrowed to the `<template>` block.

**Test result.** 46/46 pass, 2,024 assertions.

**Classification.** Test defect in both cases — the product behaviour was correct throughout.

### 5 — Vitest raced the dynamic content imports

**Observed problem.** 39 of 79 public-page unit tests failed reading empty provenance attributes.

**Root cause.** Each page loads its content through a dynamic import. A fixed number of microtask
flushes is a race: the first mount of a module is cold and needs several more turns.

**Correct fix.** `mountPage` takes a readiness selector and settles with `vi.waitFor`, so a genuine
load failure surfaces as a timeout rather than as a silently empty assertion.

**Test result.** 79/79 pass.

**Classification.** Test defect.

### 6 — Two `Ui01Render001` cases timed out in the full Vitest run

**Observed problem.** `/branch/cash-up` and `/finance/cash-up/{id}` exceeded the 5 s per-test
timeout during a 146 s full-suite run.

**Evidence.** Both pass in isolation in 4.5 s for the whole file (13/13). Neither component is
touched by this phase.

**Classification.** Environment/concurrency defect — transform pressure from the newly added
modules, not a product defect. No assertion was weakened and no timeout was raised. Confirmed
resolved in the final full run.

## Authorization-denial proof

Not applicable in the usual sense, and deliberately so: UI-06 adds **no** API operation, permission
key, policy or migration, so there is no new authorization decision to deny. What is proven instead
is that the public surface grants nothing:

- resolving an account host selects public content and no authority (ADR-017);
- an unknown account key renders a safe boundary and loads no content at all;
- `/register` is linked by exactly one account and by no other, asserted per account in the browser;
- an invitation CTA appears only where the registry says `invitationAcceptance: true`;
- the UI-03 authentication, session-family and account-switching suites are unchanged and green.

## Host-context proof

| Check | Result |
|---|---|
| Eight hosts × eight public paths on the built edge | 200, `text/html`, correct `data-account-key`, `no-cache` shell |
| Unknown host `attacker.test`, `unknown.servana.test` | Denied; no `data-account-key` in the response |

## Content-isolation proof

Eight accounts checked against the wrong seven each, three ways:

1. **Unit** — 8 landing mounts assert no other account key appears anywhere in the rendered HTML;
   24 legal mounts assert the source path contains this account and no other.
2. **Browser** — the same assertion over `page.content()`, plus per-document provenance attributes
   compared to `legal-link-matrix.json`.
3. **Static** — no composition module imports another account's module or the generated content
   barrel; the loader uses a static import table with no template-built specifier and rejects a
   composition whose declared account does not match the key requested.

## Image-isolation proof

`network-asset-matrix.json`: 8 accounts, **0** cross-account asset requests. The assertion is over
what the browser actually REQUESTED after scrolling the full page, not over what the markup
declares. Every image requested returned; 0 broken image responses.

## Responsive proof

`responsive-matrix.json`: 8 accounts × 7 widths = **56 cells**, all with
`no_horizontal_overflow: true`. At every width exactly one navigation affordance is visible
(desktop navigation XOR menu trigger). CSS media queries only — the contract test scans the public
surface for `navigator.userAgent`, `window.innerWidth`, `matchMedia(` and `ontouchstart` and finds
none. Zoom is never disabled (`index.html` and `spa.blade.php` carry no `maximum-scale`).

## Accessibility proof

`accessibility-matrix.json`: **26 axe runs** — 8 landing pages in light, 8 in dark, 8 FAQ pages, and
a representative legal page in both themes — with **0 serious and 0 critical** violations. No rule
was suppressed. Additionally proven in the browser: the skip link is the first tab stop and reaches
the single `main` landmark; exactly one `h1` per page; the mobile menu trigger is ≥44×44, opens a
modal dialog, moves focus in, keeps focus inside across twelve Tab presses, closes on Escape and
restores focus to its trigger.

## Theme proof

`theme-matrix.json`: 8 accounts. Under an emulated **dark** operating system, a fresh context
renders **light** on all eight. An explicit toggle applies dark and writes `servana.theme`; the
choice survives a reload and is applied before hydration by the pre-existing bootstrap script. The
anonymous preference stays per-browser; no account-crossing server persistence was added.

## Corrective screenshot-evidence commitment

**Committed after the completion commit, in one corrective commit
(`ui-06: commit focused screenshot evidence`).**

**Root cause.** UI-02, UI-03 and UI-04 commit their PNGs beside their index, under
`docs/frontend/audits/<phase>/screenshots/`. UI-06's capture helper instead wrote to
`docs/proof/ui-06/` (`SHOTS` in `tests/e2e/ui-06-public-landing-pages.spec.ts:30`, path recorded at
line 224) while its index was written to `docs/frontend/audits/ui-06/screenshot-index.json`. The
completion commit therefore committed all 33 PNGs — but under `docs/proof/ui-06/`, so a verifier
reading the established audits-tree convention counted **zero** PNGs under
`docs/frontend/audits/ui-06/`. The evidence was never missing; it was committed at a path that
diverged from the convention the other UI phases follow.

**Recovery, not recapture.** The 33 real PNGs already existed and were already committed. Each was
verified to be a real PNG by file signature (`89 50 4E 47 0D 0A 1A 0A`) and each SHA-256 was
verified to equal the hash the capture spec recorded in `7877e7b`. The byte-identical files were
copied into `docs/frontend/audits/ui-06/screenshots/`, hash-verified again after the copy, and
committed there. **No Playwright run was performed for this correction**, no screenshot was
recaptured, recompressed or regenerated, and no landing image, logo, fixture or unrelated product
asset was presented as a page screenshot.

**Index.** `screenshot-index.json` keeps its existing schema and record count (33). Each record now
carries `account`, `host`, `surface`, `purpose`, `route`, `viewport` (plus `viewport_width` /
`viewport_height`), `theme_requested`, `theme_rendered`, `path` and `file` pointing at
`docs/frontend/audits/ui-06/screenshots/`, `bytes`, `sha256`, `source_commit`, `captured_at` and
`data_provenance`. `also_committed_at` names the byte-identical copy that remains at the original
`docs/proof/ui-06/` path, so **no committed UI-06 PNG is unreferenced by the index**. `host` is the
production account host whose context the capture installed — not the origin the browser was
pointed at, which stays `http://localhost:4173` in the `origin` field.

**These screenshots are focused implementation evidence. They are not release-approved visual
baselines.** They record what UI-06 built, at the moment it was built, against a Vite preview
origin. UI-16 owns reviewed visual baselines and the visual-regression gate; nothing here may be
treated as an approved baseline, a sign-off, or a substitute for that gate.

**Scope.** The corrective commit changed only `docs/proof/ui-06.md`,
`docs/frontend/audits/ui-06/screenshot-index.json` and
`docs/frontend/audits/ui-06/screenshots/*.png`. No product behaviour, route contract, API,
permission, policy, migration, tenancy rule, financial calculation, generated-content authority,
landing/FAQ/legal source, image authority, authentication boundary, CI workflow or gitleaks policy
was touched, and the original completion commit `7877e7b` was not amended, rebased or replaced.

**Residual.** The capture helper still writes to `docs/proof/ui-06/`, so a future run of the UI-06
spec will regenerate the index pointing back at that path. Correcting the spec is outside this
correction's allowed paths; it is recorded as `UI06-AUDIT-003` for the owner of the next UI phase
that touches this spec. Because the generator `scripts/generate-ui06-artifacts.mjs` does not emit
`screenshot-index.json`, no `--check` staleness gate is affected by this edit.
