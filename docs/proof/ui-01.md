## 7. Audit methodology

Defined in full in [`docs/frontend/audits/ui-01/README.md`](../frontend/audits/ui-01/README.md).
In summary:

- **Two origins, never conflated.** `preview` (`http://localhost:4173`, SPA-as-web-root, stubbed
  API) and `served` (`http://localhost:8099`, the real production nginx image). Every route visit
  and every screenshot is labelled with the origin that produced it.
- **Page-claim classification.** Every one of the 123 screen-inventory rows receives exactly one
  of `true`, `false`, `unreachable`, `stale` or `not_claimed`. A row the inventory does not claim
  is `not_claimed`, never `false`.
- **The required 160-page contract is a separate register** using `claimed_by_route` /
  `not_claimed`, and the two registers are never summed.
- **Severity and root cause.** `critical` / `high` / `medium` / `low` / `observation`;
  `root_cause_status` is `proven` or `unproven` and speculation is never presented as fact.
- **Deterministic collection.** Volatile host state is captured once by `--capture` into a
  committed evidence file; the default pass is pure and `--check` proves a second pass is a no-op.

### Role fixtures

The repository's own approved browser fixtures were used (`tests/e2e/support/releaseAudit.ts`,
`stubBootstrap`). **No production credentials were invented and no real account was created.**
This carries a limitation that is itself recorded: role resolution has only ever been proven
against a stubbed `/me`, so the audit's role findings are statements about frontend routing, not
about backend authorization. Backend authorization remains proven by the feature, authorization
and tenant-isolation suites and was neither weakened nor re-litigated here.

### 9.3 Navigation and role resolution

Navigation placement matches the contract for **all eight** accounts: Super Administrator renders
**header** navigation, the other seven render **sidebar** navigation at 256 px. The typed registry
(`roleNavigation.ts`, 102 items) and the generated fixture (`role-navigation.yaml`, 102 items)
show **zero drift**, and there are **no dead links** — 88 live items all resolve to registered
routes and 14 planned items carry no route by design.

Five route targets are shared by multiple labels (`platform.billing-settings`,
`platform.registration-monitoring`, `personnel.sms`, `branch.list`, `search`), so distinct contract
pages collapse onto one screen (`UI01-NAV-001`). The Branch account renders 5 disabled entries out
of 7 visible (`UI01-NAV-003`). Human Resource has no shell of its own and reuses `BranchLayout`
(`UI01-NAV-002`).

**Cross-role surface exposure.** All seven merchant-side accounts requested `/platform` and the
router **rendered the Super Administrator landing in full**. The `/platform` route tree declares
`beforeEnter: [requiresAuth]` only; the `requiresRole` guard that exists in `router/guards.ts` is
never applied to it. The reverse direction is correctly refused — `super_administrator` requesting
`/merchant` is redirected to `/` by `requiresActiveMerchant`. Recorded as `UI01-ROLE-001` (high).
This is a UX-level exposure: the platform API independently enforces `ResolvePlatformContext`,
`EnsurePermission`, MFA and step-up, and UI-01 neither weakened nor tested that boundary.

### 11.1 Corrupted build directory — evidence discarded and recollected

**Symptom.** The first complete audit run reported all 158 route visits as `blank` and captured
only 2 of 141 screenshots.

**Not accepted as a product defect.** The repository's own `role-entry-surfaces.spec.ts` failed
identically (10/10), which ruled out the new harness as the cause but also contradicted CI, which
had passed 846 Playwright tests at this exact tree.

**Root cause, proven.** The first Playwright invocation timed out waiting for its `webServer`
(`npm run build && npm run preview`, 120 s) because a local `vue-tsc` + build exceeds that budget
on this host. Playwright abandoned the wait, but the spawned `npm run build` kept running and then
was killed mid-write. `vite build` empties `outDir` before writing, so `public/spa` was left
holding `index.html` from the 10:21 build, 251 of 259 asset files from the aborted 10:32 build,
and no `.vite/manifest.json`. The shell still served with HTTP 200 while its entry chunk 404ed.
Evidence: file mtimes, the asset-count drop, the vanished manifest, and a browser probe naming the
exact missing chunk (`/assets/apiClient-B_JkGpjw.js`).

**Remediation.** `public/spa` was removed, rebuilt cleanly, and verified: 259 assets, manifest
present and hashing to the same `43a1608a…`, and every `/assets` URL referenced by `index.html`
confirmed to exist. The preview server was pre-started so Playwright reused it rather than racing
another build. **All evidence from the corrupted window was discarded and recollected.** The
committed evidence is entirely from clean-build runs.

The missing build-integrity guard is a genuine product-side gap and is recorded as
`UI01-PROV-005`. The 120 s `webServer` timeout is environmental — CI builds within it — and no
shared configuration was changed.

### 11.2 Harness defects, found and corrected inside the harness

| Defect | Symptom | Fix |

### 12.3 Failed runs — every one classified

No failure is called a flake merely because a rerun passed. Where a cause is proven, it is named;
where it is not, that is stated plainly.

#### (a) Backend parallel, first run — 1 failed. **Cause proven: self-inflicted concurrency.**

`php artisan test --parallel` reported *1 failed / 8 skipped / 2,404 passed*, traced to
`tests/Pest.php:1004` (the Phase 22 `searchScenario` helper). Investigating it, a follow-up
`tests/Feature/Search` run failed with:

```
SQLSTATE[40P01]: Deadlock detected
Process 10783 waits for AccessExclusiveLock on relation 3159671 of database 16384;
  blocked by process 10784.
Process 10784 waits for RowExclusiveLock on relation 3159297 of database 16384;
  blocked by process 10783.
(SQL: drop table "public"."appointments", … cascade)
```

That is two `php artisan test` processes contending for the **same** PostgreSQL database while
`RefreshDatabase` drops the schema — and it was my error: a background isolated run was still
alive when a second run was launched. Evidence for the classification: the deadlock names two
concrete PIDs on one database; an earlier isolated search run exited **0**; and once every run was
serialised, **both** the serial and parallel suites passed at 2,405 / 8 / 0 with identical
assertion counts. No code changed between the failing and passing runs.

**Corrective practice:** only one test process on this host at a time. This is the same class of
constraint Phase 23 recorded for Playwright, and it applies to the backend suite too.

#### (b) Playwright, first full run — 1 failed. **Cause NOT proven.**

`appointments.spec.ts:117` — `getByRole('heading', { name: 'Appointments' })` was not visible
within the 5,000 ms expect timeout on the first navigation to `/front-office/appointments`.
Retries are 0 locally, so there was one attempt.

Not reproducible: the same file passes **13/13 in 11.9s** in isolation (that one test in 1.4s), and
a **second full-suite run passed 862/862 in 22.0m** with no code change in between.

I am **not** claiming a proven root cause. A cold first-navigation chunk load on a loaded host is
consistent with the evidence, but nothing here demonstrates it. It is recorded as an unexplained,
non-reproducible timeout with three independent clean observations against one failure — not as a
product defect, and not as a proven flake. If it recurs, `UI01-A11Y-001`'s owner phase (UI-16)
should treat it as a stability finding for the release browser gate.

#### (c) Build directory corruption during evidence collection

Fully described in §11.1. Cause proven; all affected evidence was discarded and recollected.

#### (d) Audit-harness defects
