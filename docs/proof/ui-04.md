### The three defects UI-04 found

**`UI04-TOKEN-001` (medium).** Sixteen `var(--custom, #hex)` fallbacks across fourteen pages
referenced custom properties that were **never defined anywhere**: `--color-danger` and
`--color-focus` exist in no stylesheet. The literal fallback was therefore **live**, not dead —
those pages rendered a non-brand `#dc2626` and a generic blue `#2563eb` focus ring, neither a
Servana token, neither with a dark-theme value, and neither ever contrast-checked. All sixteen
migrated onto semantic tokens; the raw-value guard now fails the build on recurrence.

**`UI04-TOAST-001` (medium).** `SvToast` carried four contract defects: colour-only status; a live
region nested inside a live region, announcing every message twice; positioning inside the band
the fixed footer occupies, so its dismiss control could be covered (a case ADR-024 names
explicitly); and removal scheduled only on mount, so any toast added later never expired.

**`UI04-POPOVER-001` (low).** `SvPopover` registered its Escape and outside-click listeners only
from a watcher on `open`. Because `open` is a caller-controlled prop, a popover mounted **already
open** never registered them — both dismissal paths dead for exactly the case where the panel is
visible from the first frame.

## Permissions changed

**None.** UI-04 makes no permission-matrix change and adds no permission key. Changing your own

request contract carries no user identifier at all —
`ThemePreferenceApiTest` proves a payload carrying `user_id`, `user`, `ulid` and `email` writes
only the caller's record, and that the route carries no permission middleware.

## Migrations changed

One, expand-only: `2026_08_01_000001_add_theme_preference_to_users_table.php`. Adds
`users.theme_preference varchar(5) NULL` with `CHECK (theme_preference IS NULL OR
theme_preference IN ('light','dark'))`. No shipped migration was edited (guardrail 12). The data
dictionary entry was written **before** the migration
(`docs/architecture/data-dictionary/core-identity-and-tenancy.md`).

Nullable with **no default** deliberately: `null` means "never chose", which resolves to light. A
stored default would be indistinguishable from a real choice.

## Accessibility proof

axe on the shared component fixture: **0 serious, 0 critical** in light, in dark, and at 360px.
Contrast is computed rather than asserted — **37** requirements evaluated in both themes by
`DesignTokenContrastTest`, which caught three real failures on its first run and led to the
separate `color-border-input` token held to WCAG 1.4.11's 3:1.

Two requirements were added late, each because the **release-wide** axe matrix found a real failure
the contract had not been asked to cover: `text-primary-on-warm` (`UI04-TOKEN-002`) and
`text-on-brand-hover` (`UI04-TOKEN-003`). That is the honest lesson of this gate — a computed
contrast contract is only as good as the pairings it enumerates, and the two it missed were both
pairings that pass in one theme and collapse in the other. The final release-wide run is the
authority: **890 Playwright tests, 0 failures**, with the axe matrix clean in light and dark across
all eight accounts, at 360/768/1280, including every screen carrying the shell.

Keyboard behaviour proven in unit and browser tests: dialog focus entry, containment, Escape and
**focus restoration to the invoking control**; drawer likewise; menu Down/Up/Home/End with
disabled items skipped; tabs roving tabindex with automatic and manual activation; accordion
heading-plus-button structure; tooltip Escape dismissal without moving focus (WCAG 1.4.13);
combobox `aria-activedescendant` with Escape keeping focus in the field; profile menu and account
switcher Escape with focus restoration; footer links last in document order.

Every icon-only control carries a required accessible name; every decorative icon is
`aria-hidden`; status is never colour-alone in any component.

### Final-gate backend failures, in full (records 23–27)

The last gate sequence began with a full serial run that reported **7 failed, 9 skipped, 2,636
passed (18,243 assertions)** in 2,633s. The terminal tail survived; the body did not. Rather than
re-running with stop-on-first-failure seven times, the suite was re-run once with the complete
output captured to a file, which recovered every failure in one pass.

The seven were **three** distinct causes, and — importantly — the set was **not stable between
runs**, which is itself the evidence for cause C.

**A. `MigrationManifestTest.php:44` — one failure, deterministic (record 23).**
`database/migrations/2026_08_01_000001_add_theme_preference_to_users_table.php`, added in
Increment 3, was never declared in `docs/architecture/migrations/manifest.yaml`. ADR-004 makes that
manifest the authoritative inventory and the lint exists precisely to catch a migration that ships
undeclared. Isolated result: **failed** — so this was never order-dependent. Correction: the full
`business_migrations` entry (table, domain, `owner_phase: "UI-04"`, `change_type: expand`,
data-dictionary reference, `depends_on`, forward-repair posture, and the closed-vocabulary
rationale). Focused result: **6 passed**. Docs only; no runtime source changed.

**B. `Tests\Unit\BrandContrastTokenTest` — five failures, deterministic (record 24).**
`brandToken()` read `--color-<name>: #rrggbb` out of the first `:root { … }` block of
`resources/spa/src/style.css`. Increment 2 moved every raw colour into the single token authority;
`style.css` now declares **no colour at all** (`grep -c -- '--color-.*#'` → `0`) and merely imports
`styles/generated/tokens.css`. So the extractor matched nothing and all five AA assertions failed
before they could evaluate. This is a test bound to a location UI-04 legitimately moved, **not** a
contrast regression — the guarantees it encodes are real and were kept. The extractor now reads the
generated authority and resolves the one alias hop the legacy names became
(`--color-primary: var(--sv-color-brand-primary)` → `#F97316`), which is exactly how a browser
resolves it, so the assertion lands on the colour that actually paints. **Every threshold is
unchanged**, including the recorded ADR-009 decision that white-on-orange fails AA. Focused result:
**5 passed (33 assertions)**.

**C. `AuditMutationCoverageTest` — one failure, deterministic (record 25). The route defect.**
`Unmapped mutating route(s): auth.preferences.update`. Plan §70's registry requires every
implemented mutating `/api/v1` route to be classified `AUDITED` or `EXEMPT`; UI-04 added
`PATCH /api/v1/auth/preferences` in Increment 3 and never classified it. This is a genuine
governance gap in UI-04's own work, and the guard did its job. The handler was inspected before
classifying: `UserPreferencesController::update()` emits no typed audit event, and there is no
`AuditEvent` case for a display preference. It is therefore `EXEMPT` with an explicit reason,
following the existing `service-sessions.notes` precedent — the subject is the authenticated user
themselves, the only writable value is a closed `light|dark` enum, it grants nothing and cannot
address another user. Minting a new audit event would write an append-only hash-chained row for a
cosmetic setting. **No route, permission, policy or authorization behaviour changed.** Focused
result: **5 passed**.

**D. `BranchPersonnelOptionsTest` — the genuinely order/randomness-dependent pair (records 26, 27).**
This is the failure that "passes alone but fails in the full suite", and it is a **pre-existing
Phase 23 fixture defect that UI-04 did not cause** — the file was untouched by this phase until
these corrections.

*Record 26, ordering.* The test asserts `data.0.display_name === 'Alpha Able'`. The Branch
Manager's own staff profile is in the same branch and `branchStaff()` gives it a **faker**
`display_name`; the endpoint orders by display name. The run drew `'Alexandria Robel'`, which sorts
before `'Alpha Able'` (`'Alex…'` < `'Alph…'`) and took row 0. So the assertion depended on the
faker draw, not on the ordering contract it claims to test. This is also the decisive evidence that
the failing set was unstable: between the two serial runs the manifest failure was fixed yet the
total stayed at seven and the assertion count moved 18,243 → 18,239, because this test flipped from
passing to failing on a different draw. Correction is at the fixture layer and local to the test —
the shared `branchStaff()` helper is untouched, since changing its default would reach many suites.
The Branch Manager's profile is pinned to `'Manager Mike'`, which sorts *between* the two fixtures,
and a new assertion pins the whole ordered result (`['Alpha Able', 'Manager Mike', 'Zebra Zulu']`),
so a random name reappearing fails loudly instead of intermittently.

*Record 27, the mirror image.* Re-running the file in isolation surfaced a second latent defect in
it: `expect($body)->not->toContain((string) $personnel->id)` — a raw substring search for the
internal numeric primary key. In isolation the sequence is small, the PK is `5`, and `5` occurs
inside almost any ULID, so it failed; in the full suite the sequence is large enough to miss, so it
passed. **It never tested what it claimed** in either direction. The intent — the internal PK must
never be the identifier handed out — is now asserted structurally: every returned `id` must match
the ULID shape `/^[0-9A-HJKMNP-TV-Z]{26}$/`, which a numeric PK cannot satisfy. That is both
deterministic and strictly stronger than the substring search. Focused result: **12 passed
(36 assertions)** in isolation.

Neither D correction touches product code, authorization, tenancy or the endpoint's narrow
`{id, display_name}` contract.

**E. The parallel gate then diverged from the green serial gate (record 28).**
With serial at **0 failed**, `--parallel` reported **8 failed** — five in `DesignTokenContrastTest`
and three in `DesignTokenGenerationTest`, every one of them
`Call to undefined function ui04Tokens()`.

This is a **UI-04 test-architecture defect**, not a flake and not a reason for a serial-only
exception. A Pest file-scope `function` is a global, but it exists only once the file declaring it
has been loaded. `ui04Tokens()` — the reader for the token authority — was declared in
`DesignTokenSchemaTest.php` and consumed by **four** specs. In serial every file loads, so the
helper always resolves. Under `--parallel` each ParaTest worker loads only its own slice, so any
worker that received a consuming spec without the declaring one fatalled. That also explains why
`WebAppManifestContractTest` consumes it yet passed: its worker happened to receive both files.
The failure is therefore a property of file distribution, which is exactly why it never appeared
serially.

An audit of every file-scope function declared under `tests/` found `ui04Tokens()` to be the only
genuine cross-file helper (the one other candidate, `consume`, is `$service->consume(...)` method
calls, not a global). It was moved to `tests/Pest.php`, the repository's existing home for shared
test helpers, with the reason recorded at the definition and a pointer left where it used to live.
The four specs are unchanged otherwise, no assertion was weakened, and **no serial-only
classification was introduced** — the requirement that serial and parallel agree was met by fixing
the cause.

### The full Playwright gate (records 30, 31) — six defects, five of them real

The earlier full Playwright result recorded in this phase was read from a **truncated terminal
tail** showing `726 passed, 0 failed`. Run against the final source tree with the complete output
captured, the suite reported **166 failed / 724 passed**. The passing counts are almost identical,
so that tail almost certainly hid the same failures rather than the tree having regressed since.
**The earlier clean-run claim is retracted**; what follows is measured.

Three runs were needed, each ending in a proven cause rather than a rerun:

| Run | Result | What it proved |
|---|---|---|
| 1 | 166 failed / 724 passed | Four causes, below |
| 2 | 17 failed / 873 passed | Two further causes, all on `super_administrator` |
| 3 | **890 passed / 0 failed / 0 flaky** | Final |

**`UI04-TOKEN-002` — one mispaired token caused 103 of the 166 failures.**
`SvProfileControl`'s initials chip carried `bg-sv-surface-warm` with `text-sv-text-on-brand`.
`text-on-brand` is Brand Deep `#4A2208` and is **fixed across both themes** — it is the label
colour for the brand colour. `surface-warm` is a pale cream in light (so the pairing looked fine)
but a dark slate `#273340` in dark, giving **1.07:1** on every screen that renders the shell. The
chip sits on a surface, so it now takes `text-sv-text`, which flips with the theme. A sweep of
every `text-on-brand` usage confirmed this was the only non-brand background; the rest sit on
`bg-sv-brand` correctly. A `text-primary-on-warm` requirement was added so the pairing is gated
rather than merely fixed.

**`UI04-RESP-001` — the shell header overflowed at exactly the tablet boundary (~30 failures).**
`scrollWidth 775 > clientWidth 768`. The profile control's identity block is `hidden md:block`, so
768px is the first width at which it appears, and an `inline-flex` trigger sizes to its content —
`truncate` never engages without a bounded width, so a long name made the trigger 562px wide and
pushed the header past the viewport. Added a `profile-identity-max-width` layout token (wired
through Tailwind, so the cap comes from the token authority rather than a literal) plus `min-w-0`
on the shrinkable ancestors, letting the text ellipsise instead of dictating header width.

**`UI04-TOAST-002` — the toast stack was announced but unaddressable.**
`UI04-TOAST-001` correctly removed the nested live region, but it removed `role="status"` from the
toasts and left only `aria-live` on the container. `aria-live` confers **no role**, so the stack
could not be found by role at all and two `queue.spec.ts` assertions broke. `role="status"` now
sits on the **same element** as `aria-live` — one region, no nesting. The unit spec had locked in
`[role="status"]` length `0`, which encoded the accident rather than the property; it now asserts
exactly one live-region element, that it carries both attributes, and that nothing inside it is
itself a live region.

**Two fixture-level corrections.** The component gallery renders both `SvThemeToggle` variants, so
the shared `theme-toggle` id resolved twice; each variant is wrapped rather than changing the
component's contract, since a product page ships exactly one. And `CashUpDetail.vue` had a bare
`overflow-x-auto` with no keyboard reachability — the contract `SvDataTable` already applies to its
own scroll container (`tabindex`, `role="region"`, label) was applied there too.

**`UI04-A11Y-001` — the Super Administrator header (run 2, all 17 failures).**
`AppShell` renders the header `bg-brand-deep text-white` for the one account that uses header
navigation, and `bg-surface` for the other seven. `SvProfileControl` hard-coded `text-sv-text`
(`#1F2933`), putting dark text on the deep-brown bar at **1.07:1** on every platform screen. The
identity text now **inherits** its colour, resolving to page text on a surface and to white on the
brand bar, with the secondary line keeping hierarchy through opacity so no second colour is pinned.

**`UI04-TOKEN-003` — every primary button's hover state failed AA in light mode.**
`color-brand-primary-hover` was `orange-800 #9A3412`; against the CTA label, which ADR-009 fixes to
Brand Deep because white-on-orange fails AA, that measures **1.89:1**. The contrast contract gated
`text-on-brand` on the *base* brand colour only, so the hover shade was never checked. Since the
foreground cannot move, the hover must **lighten**: light theme now uses `orange-300 #FDBA74`
(**8.17:1**), which the dark theme already used, making the rule "hover lightens" true in both.

> **Flagged for review.** This changes a visible brand shade. It touches **none** of the seventeen
> approved brand palette values — `#9A3412` was a UI-04-derived shade annotated "brand primary
> hover on light surfaces" — and it is forced by CLAUDE.md guardrail 11, which makes AA in both
> themes a release gate. A `text-on-brand-hover` requirement now gates both themes. If the product
> owner prefers a darkening hover, the only conforming alternative is a different CTA label colour,
> which would reopen the ADR-009 decision and is not UI-04's to make.

### Meilisearch local-environment remediation (record 32)

The final backend parallel gate reported **3 failed** — `SearchEngineIntegrationTest` (two
`InvalidResponseBodyException`) and `SearchCommandTest` ("Meilisearch is not reachable") — while the
serial gate was green. It reproduced, so it was not treated as a flake.

**Root cause, measured not assumed.** The local development Meilisearch held **4,745 indexes**, of
which **4,742** were leaked per-run test indexes. `/health` answered in 1.6 ms — which is why the
container reported healthy and the cause stayed hidden — but index *lifecycle* operations did not:

| Operation | Before | After |
|---|---|---|
| `/health` | 0.0016 s | 0.0024 s |
| `/indexes?limit=1` | 0.89 s | 0.0022 s |
| `/stats` | **17.51 s** | 0.0043 s |
| create one index | **9.92 s** | 0.307 s |
| delete one index | **4.36 s** | 0.376 s |

Under four parallel workers, each creating and dropping its own uniquely prefixed indexes, those
latencies exceed the client's timing tolerance. Serial passes because it never overlaps them. The
task queue was empty throughout (0 enqueued, 0 processing), so this was index-count cost, not
backlog.

**Classification: local environment contamination.** Not a product defect. No production timeout was
changed, no test was skipped or marked serial-only, and no CI exception was added. CI provisions a
fresh Meilisearch service and cannot reach this state.

**Remediation — exact-prefix deletion only**, under product-owner authorisation:

| | |
|---|---|
| Endpoint | `http://127.0.0.1:7700`, `getmeili/meilisearch:v1.10.3`, local compose container on `servana_default` — confirmed not staging, production, remote or shared |
| Authorised prefixes | `servana_p22cmd_`, `servana_p22test_` (exact, case-sensitive `startsWith`) |
| Before | 4,745 total · 3,486 `p22cmd` · 1,256 `p22test` · **3** preserved · **0** unexpected non-target |
| Deleted | 4,742 tasks submitted, **0 failed, 0 canceled, 0 pending**, 0 already-gone |
| After | total **3** · target prefixes **0** |
| Preserved | `servana_local_staff_profiles` (pk `id`, 6 docs), `servana_dbg_…_clients` (pk `ulid`, 3 docs), `servana_dbg_…_staff_profiles` (pk `ulid`, 1 doc) — settings readable, metadata unchanged |
| Manifest SHA-256 | targets `dff92cec3a631bb933a846e2e83bf84b5b1a15afa74329ba76547917eea2a9a8` · preserved `80a3cbbbf0d5c698aa24b7381d77e2ba532f6a794e62e7ff0e8d92150bacbdb6` (**identical before and after**) |
| Method | 60-index batches, 12 concurrent, each batch waited to terminal task state; a per-request re-check refused any non-target UID; idempotent |

`scout:delete-all-indexes` was **not** used, no Docker volume was removed, no data directory was
deleted, and Redis and PostgreSQL were untouched. The deletion is local runtime data; **no tracked
source file was changed for it.**

**Result.** Full backend parallel: **2,643 passed / 9 skipped / 0 failed**, 18,284 assertions, 4
processes, exit 0 — identical to serial, with no serial-only classification.

**Two conditions found while diagnosing, both recorded rather than papered over.**

*The search teardown leaks its own indexes.* `SearchCommandTest` and `SearchEngineIntegrationTest`
both tear down with `$client->getIndexes()`, which uses Meilisearch's **default page size of 20**.
With four workers each holding uniquely prefixed indexes, a test's own index is frequently absent
from that first page and is never deleted — the mechanism that accumulated 4,742. A full parallel
run leaves ~45. That rate does not block completion, so **no tracked test change was made here**;
it is recorded as residual risk `R8` for the search-test owner.

*A pre-existing PostgreSQL lock ceiling.* A search-only parallel run surfaced
`SQLSTATE[53200] out of shared memory … max_locks_per_transaction`. `max_locks_per_transaction`
(64) × `max_connections` (100) gives a 6,400-slot lock table, while `servana_test_1` holds 1,250
relations; four workers each dropping ~100 tables plus their indexes and toast in one transaction
sit close to that ceiling. It did **not** occur in any full-suite parallel run, where the
drop/create pattern is far less dense. Unrelated to UI-04 and to Meilisearch; no setting was
changed. Recorded as residual risk `R9`.

**Staleness.** Records 23, 24, 26, 27 and 28 changed documentation and test files only. Record 25
changed one PHP registry constant (`AuditMutationCoverage::EXEMPT`), which is read only by its own
guard — it registers no route, alters no middleware and emits nothing at runtime.

That file nevertheless lives under `app/`, which **is** a production image input, so the images
built before these corrections no longer correspond to the final source tree and the production
smoke was re-run against a rebuilt pair rather than asserted from the earlier build. **No frontend
source, asset, token, generated artifact, Nginx configuration or dependency lockfile changed**, so
the Vite manifest, the token hashes and the browser evidence captured earlier in the phase remain
valid; the rebuild exists to keep image identity truthful, not because runtime behaviour moved.
Pint (1,753 files) and Larastan level 8 (1,341 files) were re-run afterwards and are clean.
