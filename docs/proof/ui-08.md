### Proven root cause — why SMS pricing needs its own series

`COR-UI08-001` prefers extending `platform_billing_settings.settings` and permits a dedicated table
**only on proof**. The proof, against code at `16d544c5`:

1. Every row is a **complete** configuration snapshot; resolution picks exactly one row (greatest
   `effective_from <= now()`). There is no per-field effective dating.
2. **Two** authorities write the same series — `UpdatePlatformBillingSettings` and
   `UpdatePlatformSettings` — each carrying the other's fields forward, both hard-coding
   `'effective_from' => now()`.
3. A future-dated SMS row must therefore snapshot the other fields *at authoring time*, so any
   billing-mode / trial / grace / currency / settings change landing in between would be **silently
   reverted** when the SMS row became current. Those fields drive subscription invoicing, so the
   regression would be financial.
4. `UNIQUE(effective_from)` structurally couples the two scheduling streams.
5. Adding future dating to the shipped writers would change shipped financial behaviour — outside
   this decision and outside CLAUDE.md §9.

`/billing/sms` requires a **scheduled next rule** with overlap protection, so immediate-only writes
are not an option either. → dedicated `platform_sms_billing_rules`, which stores **no currency**
(the effective `platform_billing_settings` version remains the single currency authority) and is
guarded append-only with a pending-only cancellation path.

## Increment 3 — SMS Billing Settings backend (`/billing/sms`)

### Pricing authority

`platform_sms_billing_rules` — a dedicated effective-dated series, created only after the five-point
proof recorded under Increment 2b. It stores **no currency**: the effective
`platform_billing_settings` version remains the single currency authority.

The genesis migration backfills exactly one rule from `config('sms.pricing.unit_cost_minor')` at
`2026-07-22T00:00:00Z` — the day `sms_billing_entries` was created — so the entire existing usage
history resolves to the rule that actually produced its snapshots. Nothing is recalculated. When no
platform-staff user exists (a database whose seeders have not run) the backfill is skipped rather
than attributing the rule to a fabricated actor.

**`SmsCostCalculator` was rewired to the versioned authority.** This is the corrective change the
readiness audit's measured gap called for: the unit price was deployment configuration, so it was
neither versioned, effective-dated, audited nor schedulable. Config now serves only as the genesis
bootstrap when the series is empty — a scheduled rule always wins, pinned by
`it('always prefers a scheduled rule over deployment configuration')`. **The arithmetic is
unchanged**: `amount_minor = quantity x unit_cost_minor`, integer minor units, same `Money`
multiplication.

### SMS snapshot immutability

| Guarantee | Enforcement |
|---|---|
| A charged entry is never re-priced | The rule is resolved at the usage instant and snapshotted once; `sms_billing_entries_guard` freezes every monetary column |
| A settled pricing rule is never edited | `platform_sms_billing_rules_guard` freezes every pricing/ownership column |
| A pricing rule is never deleted | The same trigger raises on `DELETE`, always |
| A scheduled rule may be withdrawn only before it takes effect | The trigger refuses a cancellation once `effective_from <= now()` |
| A cancellation is never half-stated | `platform_sms_billing_rules_cancellation_check` |
| Two rules never claim the same instant | `UNIQUE (effective_from)` |

Proven at the **database**, not merely at the service layer:
`Ui08SmsBillingSnapshotImmutabilityTest` writes through raw SQL and expects the trigger to raise.

### SMS privacy proof

`it('never exposes a recipient, phone number or message body on any SMS billing route')` fetches all
four read endpoints and asserts the response body contains none of `phone`, `msisdn`,
`recipient_list`, `message_body`, `phone_encrypted`, `phone_last_four`.
`Ui08NoForbiddenPlatformCapabilityTest` additionally asserts no platform route matches
`recipient|contact|phone|message-body|export`. The usage projection joins `personnel_sms_campaigns`
for its COUNT columns only — the encrypted body and the recipient table are never touched. No
provider credential, raw callback or contact export exists anywhere in the scope.

### Tax is disclosed, never charged

`sms_billing_entries` carries the shipped CHECK `amount_minor = quantity * unit_cost_minor`, so
folding tax into a charged amount would violate it. `tax_basis_points` is therefore a disclosure
rate: it appears in the generated cost notice and in the reconciliation projection under separate
labels, and is `NULL` at launch. Proven by
`it('discloses a configured tax separately and never folds it into the charge')` — 10 units x 250 =
2,500 charged, 400 disclosed, 2,900 disclosed total, with the charge staying 2,500.

### Currency unification (an inconsistency found and closed in passing)

`SmsCostCalculator` read `sms.pricing.currency` while the platform surface read the
`platform_billing_settings` version — two authorities that could disagree, which would have made the
new page misreport the currency of a charge. Both now read the settings version.

### Finding 1 — `Container::resolveClass()` skips a defaulted, unbound class parameter

| Field | Value |
|---|---|
| Observed problem | With a rule scheduled at 777, `SmsCostCalculator::unitCostMinor()` returned the config value 100; `currency()` likewise ignored the settings version |
| Evidence | A reflection probe showed the container injecting `NULL` for both collaborators while `ResolveEffectiveSmsBillingRule::at()` returned the rule correctly |
| Affected files | `app/Domain/Messaging/Sms/Support/SmsCostCalculator.php`, `app/Providers/AppServiceProvider.php` |
| Root cause | `Illuminate\Container\Container::resolveClass()` (line 1327) returns a parameter's default when `isDefaultValueAvailable() && ! $this->bound($className)`. Both query classes were unbound concretes, so `?Foo $x = null` resolved to `null` |
| Why this is the root cause | The probe isolates it to the container: the query returns the rule correctly when called directly, and binding the class makes injection occur |
| Correct fix | Two explicit `$this->app->bind(...)` lines in `AppServiceProvider::register()`, with a comment naming the container behaviour so they are not later removed as redundant autowiring. The nullable defaults stay so the pure-arithmetic path remains directly constructible for the shipped Phase 21S unit tests |
| Tests added | `it('always prefers a scheduled rule over deployment configuration')`, `it('uses configuration only as the genesis bootstrap when the series is empty')`, `it('reads currency from the platform billing settings version, not a second SMS setting')` |
| Test result | 3 passed; `--filter=Sms` 177 passed (no regression) |
| Remaining risk | None known. Had this shipped unnoticed, every SMS charge would silently have used deployment config — the exact defect this decision exists to fix |

### Finding 2 — a raising trigger poisons the whole test transaction

PostgreSQL aborts the transaction on `RAISE` and `RefreshDatabase` wraps each test in one, so the
first expected guard violation made every later query in that test fail with *"current transaction is
aborted"*. `ui08ExpectGuardViolation()` wraps each expected violation in a nested `DB::transaction()`
— a SAVEPOINT — which rolls back to the savepoint and leaves the outer transaction usable. No
assertion was weakened; the suite still writes through raw SQL and still requires the trigger to
raise.

## Increment 5 — Internal Platform Access backend (`/platform-access`)

### Data model

Three new tables plus one expand migration, each created only after proving no existing structure
could carry it (recorded in `docs/architecture/data-dictionary/platform-governance.md`):

| Table | Why it could not be reused |
|---|---|
| `platform_access_memberships` | `users.is_platform_staff` is a bare boolean — no status vocabulary, no lifecycle, no actor, no reason, no timestamps. Its own migration says "set by platform seeders only". A boolean cannot answer *who granted this, when, why, and is it currently suspended?* |
| `platform_access_invitations` | `staff_invitations.merchant_id` and `.branch_id` are **NOT NULL**, and its role CHECK excludes `super_admin`. Inviting a platform administrator through it would require inventing a merchant and a branch for someone who must never hold either |
| `platform_access_permission_overrides` | `merchant_user_permission_overrides` is keyed on a NOT NULL `merchant_user_id`. A platform administrator has no `merchant_users` row by design, so that table cannot address them — and `forPlatformStaff()` applied no overrides at all before this phase |
| `session_families` / `host_sessions` | **Reused unchanged.** Only the closed `revoked_reason` vocabulary is expanded, by exactly one value |

### The `is_platform_staff` mirror

`users.is_platform_staff` is **retained** as the eligibility flag and becomes a **derived mirror** of
`status = 'active'`, written in the same transaction as every transition. That is what lets every
shipped reader — `LoginEligibilityService`, `AccountContextResolver`, `TenantContextResolver`,
`ResolvePlatformContext`, `MfaRequirementResolver` — keep working byte-for-byte while the membership
becomes the lifecycle authority. The creating migration backfills one `active` membership per
existing flagged user, so the two agree from the first instant the table exists.

`it('keeps users.is_platform_staff a faithful mirror of the membership status')` drives suspend then
reactivate through the API and asserts the flag follows both ways.

### Invitation security

| Property | Enforcement |
|---|---|
| Generation | 64 cryptographically random bytes |
| At rest | **SHA-256 only**, `UNIQUE`; `token_hash` is `$hidden`; a test scans every column of the stored row to prove the raw token was never persisted |
| Single use | `SELECT … FOR UPDATE` then a **conditional** update; a replay of a consumed token is refused |
| Expiry | 72 hours; `expires_at > created_at` is a CHECK, so an expired invitation must have been *issued* in the past |
| Revocation | Terminal; a revoked token no longer redeems |
| Resend | **Rotates the secret** — the previously emailed link dies immediately, proven by redeeming it and expecting a refusal |
| Binding | `purpose = 'platform_access'` and a closed `environment` vocabulary, both re-checked at consume time; a credential minted for `testing` is refused in `production` |
| Enumeration safety | The invite endpoint returns the **same status and the same body** for a known and an unknown address; `expect($known->json())->toBe($unknown->json())` |
| Normalization | `email = lower(email)` CHECK; a case-differing duplicate is unrepresentable |
| One live invitation | Partial unique index on `email WHERE status = 'pending'`; a second invite **rotates** the existing one rather than duplicating |

**Magic Link only.** No password, OTP or WebAuthn credential is created anywhere in this path.

### Two permissions, and only two

`platform.internal_access.view` / `.manage`, `super_admin` only, matrix total **169**. Asserted
directly: the matrix holds exactly **two** keys containing `internal_access`, and neither reaches any
merchant-side role.

### Self-escalation denial

Deny-only is **structural**, not procedural:

- `platform_access_permission_overrides_effect_check` permits only `'deny'` — a grant override
  cannot exist as a row, proven by attempting the raw insert;
- a `BEFORE INSERT OR UPDATE` trigger rejects any permission whose `permissions.category <>
  'platform'`, proven by attempting the raw insert with a merchant key;
- `PlatformAdministratorQuorum::assertNotSelf()` refuses **every** action an actor aims at their own
  membership, returning `422 platform_access.self_action_forbidden`.

`it('subtracts a deny override from the resolved platform permissions')` proves resolution actually
removes the key and adds nothing.

### Sole-administrator lockout

`PlatformAdministratorQuorum::assertRemovable()` runs inside the mutating transaction and refuses any
transition that would leave **zero** active Super Administrators, returning
`422 platform_access.last_active_administrator`. The active set is counted **under a row lock** so two
concurrent removals cannot each observe two administrators and both proceed.

### Session revocation

Reuses the R6 authority — `SessionFamilyService::revokeFamiliesForUser()`. **No second session store
was created and no token material is read.** The reason recorded is
`platform_access_sessions_revoked`, added to the closed vocabulary by this phase precisely because
`session_revoked_by_owner` and `global_logout` both describe the *user's own* action and would have
written a false forensic record. Suspension and deactivation keep using the existing
`membership_revoked`, whose definition already covers them exactly.

`SessionSchemaContractTest` continues to assert the enum and both CHECK constraints are identical, so
the three cannot drift.

### No merchant-role assignment

- There is **no role field** on any request in this surface; a client-supplied `role_key` is ignored
  and the invitation is still minted as `super_admin` (asserted).
- `role_key` is CHECK-constrained to `super_admin` at the database.
- A lifecycle mutation writes **no** `merchant_users`, `branch_user_assignments` or `staff_profiles`
  row — asserted by counting all three tables before and after.
- Invitation acceptance is asserted the same way.

## Increment 6 — Feature Flags backend (`/platform/feature-flags`)

### Feature-flag allowlist

The catalogue is **code**: `config/platform-feature-flags.php`. The API can read it, propose changes
to it and pause a flag — it can never create a key, and there is deliberately no create route.
`PlatformFeatureFlagCatalogue::definition()` returns null for anything else, and every caller treats
null as deny.

**The shipped catalogue is empty, and that is the truthful state.** No platform feature flag has been
authorized, so the page renders an honest empty state (`meta.catalogue_is_empty: true`). Seeding a
fabricated flag to populate a screen would be exactly the production mock data UI/UX plan §15.2
forbids, and the config file says so in a comment so the next reader does not "helpfully" add one.

Each definition records owner, description, risk class, supported environments, supported target
types, dependencies, affected screen keys, affected operation IDs, health metric key (**nullable**),
rollback criterion and an optional external gate.

### Feature-flag state machine

```text
flag:            inactive | scheduled | active | paused | retired      (retired terminal)
change request:  pending | approved | rejected | cancelled | applied | failed
target type:     merchant | plan | cohort                              (closed)
```

Every transition except the clock and the emergency pause requires an **approved change request**.
There is no unaudited instant-enable path.

### Maker/checker

**A database constraint, not a convention:**

```sql
CHECK (approved_by_user_id IS NULL OR approved_by_user_id <> requested_by_user_id)
```

The decisive test bypasses policy, controller and service entirely and attempts the raw `UPDATE`
setting the requester as approver — the database refuses it, and the request stays `pending`. The
service refuses it too, with `422 feature_flag.self_approval_forbidden`.

`impact_statement`, `rollback_plan`, `health_criterion` and `reason` are `NOT NULL`, proven twice: a
request missing them is `422 validation_failed` at the Form Request, and a raw insert with nulls is
refused at the database. A partial unique index permits **one** pending request per flag.

Approval **applies** the configuration in the same transaction: the flag is written, `version`
bumped, `approved_configuration_hash` copied from the request, targets replaced, and two history rows
(`approved`, `applied`) appended under one correlation ULID. Either all of that happens or none does.

**Pause is the single deliberate one-actor path**, permitted only because it moves a flag *towards
deny* and never away from it — requiring a second approver to stop a misbehaving rollout would make
the safest action the slowest one. It still requires `platform.settings.update`, MFA, a fresh
`platform_feature_flag_change` step-up and a mandatory reason, and it appends a history row.

### Feature-flag non-bypass

`PlatformFeatureFlagEvaluator` denies at the first failure, in this order:

```text
1. code allowlist   2. environment   3. external gate   4. flag state
5. effective dates  6. target        7. rollout
```

Each step has its own test asserting the exact deny reason. Two structural proofs matter most:

- **It cannot grant.** `it('grants nothing: the evaluator answers only about rollout')` asserts the
  class's *entire* method list is `__construct, allows, decide, bucket, externalGateIsOpen`, that no
  method name contains `permission`, `entitlement`, `billing`, `authorize` or `can`, and that the
  source references no `TenantContext`, `EnsurePermission`, `PermissionResolver` or `Gate::`. It has
  no access to authorization state, so it cannot substitute for it.
- **Rollout is deterministic.** `crc32(flag_key . ':' . subject) % 10000` against integer basis
  points — never a float, never random. The same subject lands in the same bucket every time, so a
  rollout only ever widens. A partial rollout with **no** subject denies rather than flipping a coin.

Targets fail closed too: when any target exists, an unmatched or absent subject is denied rather than
quietly included.

### Gate-W non-bypass

`it('cannot open or bypass an external gate')` gives a flag every reason to allow — `active`, fully
rolled out, correctly targeted — and it still denies with `external_gate_closed`.
`externalGateIsOpen()` returns `false` with no setter, no column, no endpoint and no flag state
behind it, and a companion test asserts no `external_gates` table and no `external_gate` / `gate_open`
column exists anywhere. **A flag cannot make Wallet or Refer & Earn functionality available while
Gate W is closed.**

### Never evaluated in the browser

There is no client counterpart. A test walks every `.ts` and `.vue` file under `resources/spa/src`
and asserts rollout bucketing is not reimplemented client-side.

### Permissions

Reuses `platform.settings.view` / `.update`. **No feature-flag permission key exists** — asserted
against the live matrix, which still totals **169**. A test additionally walks every
`platform.feature-flag*` route and asserts each carries exactly one permission gate, `view` for reads
and `update` for writes.
