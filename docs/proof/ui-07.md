## Phase

`UI-07` — the corrective UI programme's route, navigation, inventory and screen-contract
foundation. Entry condition: UI-06 merged.

## Objective

Create the machine-verifiable 160-page authenticated route contract: one canonical authority for
every authenticated page across the eight accounts, deterministic projections derived from it,
route and navigation parity against the real router, and the account guard on every authenticated
account tree.

## Root-cause records

### `UI07-GUARD-001` — seven authenticated account trees rendered for any account

- **Observed problem.** An authenticated Personnel user could render the Finance, Branch, HR,
  Front Office, Audit or Merchant Administrator shell.
- **Evidence.** `requires-account-coverage.json` before the change: one guarded tree
  (`/platform`), 100 authenticated routes across eight trees.
- **Affected files.** `resources/spa/src/router/routes/{merchant,branch,hr,finance,frontOffice,personnel,audit}.ts`.
- **Affected accounts.** All seven merchant-side accounts.
- **Root cause.** UI-03 closed `UI01-ROLE-001` for `/platform` only and deferred the remaining
  trees to UI-07; the other seven kept `requiresAuth` + `requiresActiveMerchant`, neither of which
  is account-aware.
- **Why this is the root cause.** `requiresActiveMerchant` asserts a merchant is active. It has no
  account input, so it cannot distinguish Finance from Personnel.
- **Correct fix.** Attach the existing `requiresAccount(<account>)` to each tree root and declare
  `meta.accountKey` so the requirement is readable from the router record itself.
- **Tests.** `accountRouteGuard.spec.ts` (47 cases: allow, held-account mismatch, host mismatch,
  missing account, unknown account, non-enumerating denial — all eight accounts);
  `tests/e2e/ui-07-navigation-screen-contracts.spec.ts` (8 allow + 24 deny in a browser).
- **Proof of resolution.** `requires-account-coverage.json`: 9 trees, 100 routes, `0` missing.
- **Remaining risk.** None for the guard. The backend remains the boundary and was not changed.

### `UI07-ROUTE-001` — four planned pages exposed by placeholder-component routes

- **Observed problem.** `/platform/dashboard`, `/front-office/dashboard`, `/personnel/dashboard`
  and `/audit/dashboard` returned 200 and rendered a page-shaped placeholder.
- **Evidence.** All four resolved to `DashboardStub.vue` (6 lines, text *"Phase 4 stub"*). The
  generator's collision check listed exactly those four contract route names.
- **Root cause.** Phase 4 scaffolded a stub per account shell and no later phase removed them; the
  screen inventory recorded them as `implemented`, so nothing flagged the claim.
- **Why this is the root cause.** The component is a literal placeholder: it has no data, no API
  and no authorization. §7.2 requires a planned page to create no dead or fake link, and §13.5
  forbids satisfying the page count with a placeholder component.
- **Correct fix.** Remove the four routes and the four now-dead components. The contract entries
  reserve their identities as `planned`, owned by UI-08/UI-13/UI-14/UI-15.
- **Files changed.** The four route modules; `pages/{platform,front-office,personnel,audit}/DashboardStub.vue` deleted.
- **Tests.** `navigationFilter.spec.ts` (no planned page has a live route);
  `Ui07NavigationContractTest` (`contract_route_names_colliding_with_runtime` is empty); browser
  case *"no planned contract route is reachable at runtime"*.
- **Proof of resolution.** `/personnel/dashboard` now renders the not-found boundary.
- **Remaining risk.** `pages/finance/DashboardStub.vue` remains orphaned dead code — that is
  `UI01-ROUTE-006`, owned by **UI-12**, and was deliberately not absorbed here.

### `UI07-NAV-001` — a primary navigation link resolving to a parameterised route

- **Observed problem.** Three contract entries were bound to parameterised runtime routes:
  `merchant_branch.branch-profile` and `merchant_branch.branch-calendar` → `/branch/:id…`, and
  `merchant_audit.exports-history` → `/audit/exports/:id`.
- **Evidence.** Mounting the Branch navigation threw `Missing required param "id"`.
- **Root cause.** A primary navigation link is rendered from the route **name** alone. A
  parameterised target cannot resolve, so the link is dead at mount time while still type-checking.
- **Correct fix.** Those pages are `planned`: no parameter-free route delivers them today. The
  generator now **rejects** any primary entry bound to a parameterised route, so the class cannot
  return.
- **Tests.** Negative control `primary-navigation-on-a-parameterised-route`.
- **Remaining risk.** UI-10 and UI-15 must supply the parameter-free assigned-branch and
  export-history routes.

### `UI07-ENV-001` — the queue and service-session suites fail for the last minutes of each business day

- **Observed problem.** A backend `--parallel` run started at Nairobi **23:57** produced 24
  failures across `tests/Feature/Scheduling/{QueueApiTest,QueueAssignmentTest,QueueAuditTest,QueuePositionTest}.php`
  and `tests/Feature/ServiceSession/{ServiceSessionApiTest,ServiceSessionAuditTest,ServiceSessionBranchClosureTest,ServiceSessionCouplingTest}.php`.
- **Evidence.** 22 of the 24 carry the identical exception,
  `App\Domain\Scheduling\Exceptions\SchedulingValidationException: The proposed time crosses a
  business-date boundary`, raised from `QueuePersonnelAssignmentValidator::ensure` via
  `CreateWalkInAndQueueEntry`. The container's business clock read `Africa/Nairobi 23:57` at the
  time of the run.
- **Root cause.** These tests create a walk-in at the real "now" and start a session whose
  expected end is computed from the service duration. Within roughly the last hour of a Nairobi
  business day that end crosses midnight, and the business-date-boundary rule — which is correct
  product behaviour — refuses it. The tests do not freeze time.
- **Why this is the root cause.** The failure is a function of wall-clock time, not of input: the
  **serial** run of the *same* stabilized tree, finished before the window opened, passed
  2,792 / 14 skipped / 0 failed. Re-running `--parallel` past midnight passes. UI-07 changed no
  PHP application code at all — its only PHP changes are three test files, none of which touches
  scheduling.
- **Classification.** Environment / test-determinism defect. **Pre-existing**, and not a product
  defect: the application is enforcing a real business rule correctly.
- **Not fixed here.** Freezing time in the Phase 16B/16C scheduling suites is a change to another
  phase's tests with no connection to the navigation contract. Absorbing it would widen this
  phase's diff for no contract benefit.
- **Owner.** A separately authorized test-determinism correction, before Phase 25. **Risk if
  forgotten:** CI is red for anyone who runs the suite in the last hour of a Nairobi business day,
  and the failure looks like a product regression.

### Failure classifications

### `UI07-HARNESS-001` — the shared e2e harness never served the host account context

- **Observed problem.** The first full Playwright run after the guard change reported **235
  failed / 819 passed** across 26 spec files (`audit`, `appointments`, `queue`, `phase-20f`,
  `phase-20g`, `phase-20h`, `phase-21s`, `payment`, `invoice`, and others).
- **Evidence.** Every failing spec stubs `/api/v1/me` inline and navigates to an authenticated
  account route. `requiresAccount` fails closed when the server established no host context, so
  each one landed on `/access-denied`.
- **Root cause.** `vite preview` serves a static `index.html` with no Laravel shell, so the
  `servana-account-context` block is absent. UI-03 solved this in
  `tests/e2e/support/roleBootstrap.ts`, but only the eight platform-touching specs adopted it —
  every other authenticated spec kept its own inline `/me` stub with no context and no
  `account_keys`. Extending the guard to the remaining seven trees exposed all of them at once.
- **Why this is the root cause.** The guard is behaving exactly as specified: the host context is
  server-established, and its absence must deny. The gap is in the harness, not the product.
- **Correct fix.** `accountKeyForRole()` and `stubAccountContextForRole()` added to the shared
  harness — one role→account mapping instead of twenty-six copies — and called from each spec's
  own `/me` stub, alongside the `account_keys` the bootstrap already needed. The guard, the
  resolver and the account registry are untouched. Changing the injected account remains how a
  deny case is built.
- **Verification.** Four representative repaired specs (`audit`, `appointments`, `queue`,
  `phase-20f`) — 93 passed, 0 failed — then the full suite.
- **Remaining risk.** The harness accommodation is `UI01-PROV-003`, owned by UI-16: a
  deployed-origin run needs no injection because the real shell embeds the context.

### `UI07-AUDIT-001` — the Phase 23 release audit graded four screens that no longer exist

- **Observed problem.** `phase-23-release-audit.spec.ts` still generated responsive, theme and axe
  tests for `platform-dashboard`, `front-office-dashboard`, `personnel-dashboard` and
  `audit-dashboard`, and its coverage guard failed with five *missing* live screens.
- **Root cause.** Two consequences of this phase's own corrections. `SCREENS` in
  `tests/e2e/support/releaseAudit.ts` is a hand-maintained URL/bootstrap table that still listed
  the four screens `UI07-ROUTE-001` removed; and `liveInventoryScreens()` filtered
  `status !== 'planned'`, which was correct only while `planned` was the sole non-live value —
  after the vocabulary reconciliation it enrolled five `disabled_by_gate` rows that have no route.
- **Correct fix.** Remove the four entries from `SCREENS`, and filter on
  `status === 'implemented'` — the only status with a screen to grade. The audit's coverage guard
  stays strict, and no planned or gate-blocked screen was enrolled to make it pass.
- **Verification.** The `release-audit coverage` group passes: 3/3.

## Canonical authority decision

**Outcome B, narrowed.** A new handwritten authority was created:

```text
docs/frontend/navigation/servana-user-account-navigation-map.yaml
```

Rejected alternatives, with reasons:

- `role-navigation.yaml` — a *generated* mirror of `roleNavigation.ts`, holding ~100 runtime nav
  items in a `live`/`planned` vocabulary. It cannot carry the 160-page contract without becoming a
  second authority.
- `docs/frontend/source-inventory/navigation-map.json` — generated by UI-00 from the human map and
  explicitly defers owner phase and implementation status to UI-07.
- `docs/frontend/screens/inventory.json` — the **runtime** register (what is built), covering
  public, auth and access-state surfaces the 160 excludes.

**Two registers, reconciled and never summed** — the model UI-01 established and merged:

| Register | Authority | Answers |
|---|---|---|
| Contract | `servana-user-account-navigation-map.yaml` (160) | what is **required** |
| Runtime | `docs/frontend/screens/inventory.json` (122) | what is **built** |

Parity between them is asserted by `inventory-parity.json` and `Ui07NavigationContractTest`.

**Route parity, not route generation** (§18.2). The current route modules are stable, carry
page-specific lazy imports, and are matured by six phases of browser proof. Regenerating them
would rewrite that structure for no contract benefit, and the map's host-relative paths cannot be
registered in one router without host-scoped route construction — a change that would invalidate
UI-03's and UI-06's proofs and is properly each account phase's work. The contract therefore
records the **contract identity** (`route_name`, `route_path`) and, separately, the **actual
runtime binding** (`runtime_route_name`, `route_delivery`). `UI01-ROUTE-003` (path shape) stays
open, now with a per-page owner rather than one aggregate count.

Generated projections, never hand-edited:

```text
resources/spa/src/navigation/navigationRegistry.generated.ts
docs/frontend/screens/contract/{account}/{screen_key}.md   (160)
docs/frontend/audits/ui-07/*.json                          (14)
docs/frontend/navigation/role-navigation.yaml              (fixture, now a projection of a projection)
```

## Page-count contract

```json
{
  "super_administrator": 22,
  "merchant_administrator": 23,
  "merchant_branch": 18,
  "merchant_human_resource": 19,
  "merchant_finance": 24,
  "merchant_front_office": 19,
  "merchant_personnel": 20,
  "merchant_audit": 15,

```

`22 + 23 + 18 + 19 + 24 + 19 + 20 + 15 = 160`. The total is **summed from the entries**, never
written independently; the generator refuses a declared total that disagrees, and negative
controls `account-count-drift` and `total-drift` prove it.

Excluded from the count (§7.5), and left registered: public landing pages, login, registration,
Magic Link request/consume, legal pages, FAQ, generic error pages, invitation acceptance, shared
support overlays, and modal routes that are not full pages. The generated authenticated count uses
an explicit domain predicate, never a path guess.

### `UI07-GUARD-002` — the account guard was coarser than screen ownership

- **Observed problem.** Five browser cases that had always passed began failing: a Merchant
  Administrator could no longer reach the branch list, branch creation, the branch record, its
  operating hours, or staff invitations.
- **Evidence.** `docs/frontend/screens/inventory.json` records `branch-list`, `branch-detail` and
  `branch-operating-hours` as **both** `merchant_administrator` and `merchant_branch`, and
  `branch-create` as `merchant_administrator` **only**. `StaffInvitations.vue` branches on
  `auth.isMerchantAdmin()` to offer Branch Manager / Human Resource to one account and the
  operational roles to the other.
- **Root cause.** My first pass guarded `/branch` and `/hr` as whole trees using the account
  implied by the **path prefix**. A path prefix is not an account boundary. Plan §13 assigns
  branch creation to the Merchant Administrator and explicitly denies it to the Branch Manager, so
  guarding `/branch` as `merchant_branch` denied the account that owns the capability — and would
  have made a Branch Manager the only account able to reach a screen the Plan forbids them.
- **Why this is the root cause.** The tests encoded the Plan's authority boundary correctly; the
  guard encoded the URL. Re-pointing the tests would have fabricated authority, which is why
  Category D exists and why this was resolved as a product defect rather than a test defect.
- **Correct fix.** `requiresAccount(...accountKeys)` now accepts the accounts that genuinely own a
  route. The tree root admits both owners; the ten Branch-only and nine HR-only children re-assert
  their single owner on their own records. The served host account must be one of the owners
  **and** the user must hold *that* account — host and held account still have to agree, so
  nothing was widened beyond real ownership.
- **Files changed.** `resources/spa/src/router/guards.ts`,
  `resources/spa/src/router/routes/branch.ts`, `resources/spa/src/router/routes/hr.ts`.
- **Tests.** `accountRouteGuard.spec.ts` (47), `navigationFilter.spec.ts` (25),
  `tests/e2e/ui-07-navigation-screen-contracts.spec.ts` (42), plus the five restored cases.
- **Proof.** `requires-account-coverage.json` records the two shared-ownership trees, their shared
  screens, the governing authority and the guard's semantics.
- **Remaining risk.** The Merchant Administrator still renders these screens inside the Branch and
  HR shells. The canonical contract already reserves that account's own `/branches`,
  `/branches/:branchUlid` and `/staff` routes as `planned`, owned by UI-09.
